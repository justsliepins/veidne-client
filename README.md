# Veidne client

Veidne is a free mail merge tool that runs in the browser. You upload a Word template, click the words that should become fields, upload an Excel spreadsheet, and Veidne produces one personalised Word document for every row. It needs no install and no account, and the central promise of the product is that your documents and your data never leave your device.

This repository is the client, the part that runs in the browser and does the merging. It is published so that the promise can be checked rather than taken on trust. The sections below are written for a reader who wants to verify it: where the files are handled, which parts of the application talk to a server, and exactly what those parts send.

## Where the work happens

Everything that parses or rewrites the user's files lives under `src/features`. Everything that opens a network connection lives under `src/services`. The drop zone in `src/shared/components/DropZone` only checks a file's extension and size and hands the `File` object on.

The uploaded Word document is parsed in `src/features/editor/utils`. `docxDirectParser.ts` opens the `.docx` as a zip archive with pizzip and reads its XML directly to produce the words shown in the editor, the page layout and the paragraph styles. `imageFieldXml.ts` opens the same archive for image placeholders, `docxAnchors.ts` holds the walkers that locate paragraphs and runs in the parsed XML, and `normalizeFields.ts` rewrites field markup inside the archive. All of this operates on an `ArrayBuffer` that came from the file input.

The spreadsheet is parsed in `src/features/data/utils`. `excelParser.ts` reads the `.xlsx` or `.xls` with SheetJS (the `xlsx` package). `fuzzyMatch.ts` matches column names to fields and `imageMatch.ts` matches image file names to rows. `generateKitSpreadsheet.ts` builds a spreadsheet for the user to download.

The documents are produced in `src/features/generator/utils`. `documentTagger.ts` writes the field tags into a copy of the template. `documentGenerator.ts` fills one copy per row with docxtemplater and pizzip. `imageSwap.ts` and `imageTranscoder.ts` replace image placeholders using the browser's canvas. `downloadHelpers.ts` bundles the results into a zip with jszip and triggers the download. `fileNaming.ts` builds each output file name from a spreadsheet cell the user chooses, and `sourceFiles.ts` offers the user's own tagged template and spreadsheet back as downloads.

These modules import document libraries, local helpers, the feature flags in `src/config/features.ts`, the translation helper and the zustand stores. One of them, `sourceFiles.ts`, also imports the analytics function from `src/services` and reports the event `template_downloaded` with a file kind and a surface label when the user downloads their own files; no file content is passed to it. The three directories also hold a few small helpers that are not described here, for colours, types, image coverage, whether a run still needs pictures and file size formatting; none of them opens a connection.

The uploaded bytes, the parsed words and the parsed rows are held in memory in zustand stores: `src/features/editor/store/editorStore.ts`, `src/features/data/store/dataStore.ts` and `src/features/generator/store/generatorStore.ts`. `src/features/editor/utils/sessionPersistence.ts` saves an in-progress session to `localStorage` under the key `veidne_session` so that the editor can be resumed after a reload: the file name, the field definitions, the editor phase, a data-step sub-state, a kit-downloaded flag, a timestamp, an always-empty `documentHtml` leftover and, while the saved record stays under 4,194,304 characters (about 3 MB of `.docx`), the template bytes as base64. Larger documents are saved without their bytes, and demo and sample runs are never saved. The record is read back by `Editor.tsx` through the same module and is never transmitted. The client keeps a few other small flags and counters in `localStorage`, such as a running total of documents generated, whether certain hints have been shown and the PDF consent flag described below; none of them is ever sent. The one `localStorage` record that does reach a server is the first-touch attribution that `src/services/attribution.ts` keeps for the `page_view` event, described under analytics.

The quickest independent check is a search of `src` for `fetch(`, `XMLHttpRequest`, `sendBeacon`, `WebSocket` and `EventSource`. Every match is in `src/services`. The base path for the site's API is the relative constant `API_BASE_URL` in `src/config/constants.ts`.

`e2e/privacy-canary.spec.ts` is the test that guards this. It runs the full merge flow in a real browser against the dev server with the PDF feature off, using the committed fixtures, and records every request the browser context makes, with its headers and raw body bytes, together with every WebSocket. It then fails if any request went to an origin other than the dev server (such requests are aborted after being recorded, and the recorded list must be empty), if any request URL, header or body contains any string from the fixture files (every spreadsheet cell, raw and as formatted, every text run of the template, and six hand-picked ones, matched plain, percent-encoded and form-encoded), if any request body is larger than 4096 bytes, is not valid JSON posted to the analytics endpoint, contains a zip signature or the raw or base64 bytes of either fixture, or could not be read at all because it was a Blob, File or stream, if more than 16384 bytes were posted in total, if a WebSocket, worker, service worker or second tab was opened, or if an analytics body has an unexpected shape or event name. It also waits until the upload and generate events have been reported, so a leak added to one of them is judged rather than missed. Each of these checks was made to fail on purpose while writing it, by adding a third-party stylesheet, posting the file bytes, posting document text, posting a Blob, posting to another path, opening a WebSocket and sending a second cell value; every attempt failed the test with the offending URL or reason named.

## What talks to a server, and what it sends

The site's own API is reached under the relative path `/api`, which the production web server proxies to a separate backend. The backend is not part of this repository. Because the API is served from the same origin, every request to `/api` carries a cookie named `veidne_uid` that the backend sets to tell browsers apart anonymously; the `credentials: 'include'` option on most calls only keeps that true if the API ever moves to another origin. The client never reads or writes that cookie itself.

Analytics. `src/services/analyticsService.ts` posts to `/api/analytics` on user actions. Each request body is JSON with an event name, an optional `data` object and a timestamp. Every event the client can send is named in the type union at the top of that file. One name in it, `matrix_selection`, is sent by nothing in this repository: it was emitted by the former start page, where it recorded which of that page's options a visitor chose, and that page was removed from the client on 22 October 2026, four days before this repository was opened. Rows with that name in the analytics data were recorded by the versions in use before then, and a browser that still holds an older copy of the application can send it for a while after. The name stays in the union so that the list matches what the backend accepts. The `data` objects hold counts, flags and short labels drawn from fixed sets in the code. `page_view` sends the path of the page's URL on every navigation, without its query string, and on a visitor's first page view also the `utm_source`, `utm_medium` and `utm_campaign` query parameters and the hostname of the referring page, which `src/services/attribution.ts` captures once and keeps in `localStorage`. `generate_started` and `generate_completed` carry a `sample` flag when the run used the built-in sample data; `generate_completed` also sends the number of documents produced and, when the template has image fields, the number of images matched. `donation_initiated` sends the amount in euros, Stripe's live or test flag and a label for the card or page the donation started from. `template_selected` sends the template slug. `roadmap_voted` sends the id of a static roadmap item, as a string. The remaining events send a surface or source label, a file kind (`docx`, `xlsx`, or `data` for the kit spreadsheet), how images were added, a variant name, or one or more counts, or nothing. No event carries a file name, file contents, field names, column names or cell values. The call is fire-and-forget and its errors are swallowed, so the merge works when the backend is down.

Social proof counter. `src/services/statsService.ts` fetches `/api/social-proof` with a GET request and no body to show the number of documents generated so far on the homepage and the guide pages. The request carries the cookie described above and nothing else, and the counter is simply omitted when it fails.

Template library. `src/services/templateService.ts` fetches the template list from `/api/templates` and a chosen template from `/api/templates/{slug}/download`. The request contains the template slug and nothing else. If the backend is unavailable it falls back to the list embedded in the same file and to the `.docx` files in `public/templates`.

Donations. `src/services/donationService.ts` posts the chosen amount in cents, the currency and two return URLs to `/api/donations/create-session` and receives the URL of a Stripe-hosted checkout page, to which the browser is then sent. The client never loads Stripe's JavaScript and contains no Stripe key. After a donation, the thank-you page sends the session id from its own URL to `/api/donations/session/{id}` to display the amount, repeating the request every three seconds for up to a minute while Stripe's confirmation is still pending.

Suggestions and bug reports. `src/services/suggestionService.ts` posts a title, a description and the Stripe session id to `/api/suggestions`. `src/services/bugReportService.ts` posts a subject, a body, an optional email address and an optional image chosen by the user to `/api/bug-report` as multipart form data. Apart from the Stripe session id, which the thank-you page takes from its own URL, everything in both requests is typed or attached by the user; nothing else is collected automatically.

Roadmap and stats. `src/services/roadmapService.ts` defines calls to `/api/roadmap` through the generic helpers in `src/services/api.ts`, but nothing in the application imports either file; the roadmap page is static, shows no vote counts, and its vote buttons only remember the choice for the current page view and send the `roadmap_voted` analytics event above. The `fetchStats` function in `statsService.ts` is likewise unused.

PDF export, the one exception. The PDF feature works only when the build has `VITE_CONVERT_API_URL` set. `src/services/pdfConversion.ts` is the sole reader of that variable; its code is compiled into every build, but when the variable is unset the feature renders nothing and makes no calls. When it is set and the user chooses PDF, the finished Word documents are uploaded as multipart form data to `{VITE_CONVERT_API_URL}/v1/batches`, each under its output file name, with a parallel `filenames` field carrying the same name without its `.docx` extension. The documents are the merged output and contain the user's data, and the file names are built from a spreadsheet cell in each row (the column the user chose, or the first mapped column until they choose one), optionally joined with a second column's value and a prefix the user typed, so cell values reach the converter as file names as well. Progress is polled at `/v1/batches/{id}` once a second. A batch can be cancelled at `/v1/batches/{id}/cancel`; the client also sends that cancel on its own, with `keepalive`, when the page is unloaded or the user leaves the results screen while a batch is still in flight. The PDFs are downloaded from `/v1/batches/{id}/result.zip`, or for a single document from `/v1/jobs/{id}/result` with a `token` query parameter supplied by the status response. Before each conversion the user sees a consent screen, the `consent` phase in `src/features/generator/store/pdfStore.ts` rendered by `src/features/generator/components/PdfFlow/PdfFlow.tsx`, and can decline, in which case nothing is sent; ticking the box to not be asked again stores a flag in `localStorage` and later conversions skip the screen. The converter is a separate service, `https://convert.veidne.com` in production, and its code is not in this repository. What happens to the files after upload therefore cannot be verified here. The site states that they are deleted once the download is ready.

Fonts. No web font is loaded. The Fluent UI provider that wraps every page applies its system font stack to the content, and `src/design-system/global.css` sets the same stack on `body` on purpose, so a page load requests nothing from a font service or any other third party. Earlier versions imported a Google Fonts stylesheet that was never actually used for rendering; that import was the only third-party request a page load made, and it is gone.

Nothing else. No analytics script, tag manager, error reporter, chat widget, service worker or web worker is loaded. `index.html` contains page metadata, structured data and the application bundle only. The review-site links in the donation components are ordinary links that the user may click.

## Build and run

Vite 7 requires Node 20.19 or a later 20.x release, or Node 22.12 or later. Install with `npm ci` and start the development server with `npm run dev`; it listens on `http://localhost:5173` and proxies `/api` to `http://localhost:5000`, where the private backend would run. Without a backend the fallbacks described above apply and the merge itself works.

```
npm ci
npm run dev
```

`npm run build` runs the TypeScript check, the Vite build and a prerender step that builds a server bundle into `dist-ssr` and uses it to write static HTML for the homepage, the four use-case pages and the about page into `dist`. The result is a set of static files that any web server can serve; production uses nginx with a single-page-application fallback to `index.html`. `npm run preview` serves `dist` locally, though it does not map the prerendered routes the way nginx does. The `Dockerfile` builds the client and places `dist` in an nginx image; the nginx configuration that provides the `/api` proxy and the fallback is added outside this repository, so the image serves nothing on its own.

```
npm run build
```

Build-time configuration is read from environment files that Vite loads by mode. `.env.example` documents the variables; copy it to `.env.development` for the dev server or `.env.production` for a build. Both copies are ignored by git. With `VITE_CONVERT_API_URL` unset the PDF feature renders nothing, as described above.

`npm run lint` runs ESLint. `npm run test:e2e` runs the Playwright suite in Chromium (install it once with `npx playwright install chromium`). The suite starts two dev servers itself, on port 5173, which reads `.env.development`, and on port 5181, which runs in a mode named `darklaunch` for which no env file exists, so the PDF and image variables are absent there; nothing in the application behaves differently under the suite. The privacy canary runs against the second server and needs nothing else. Three of the four image specs, `image-fields`, `image-journeys` and `image-output`, need `VITE_IMAGE_FIELDS=true` in `.env.development`; `image-passthrough.spec.ts` runs against the second server and needs nothing. The PDF specs, except `pdf-darklaunch.spec.ts`, need `VITE_CONVERT_API_URL` in `.env.development`, and all but `pdf-entry.spec.ts` also need the converter running on port 8085; most expect its delay mode, and the two specs tagged `@real` expect its real mode and are meant to be run on their own with `npx playwright test --grep @real` (a plain `npm run test:e2e` runs them too, so pass `--grep-invert @real` to leave them out of a delay-mode run). `e2e/pdf-unreachable.spec.ts` additionally stops and restarts the converter with docker compose in a local checkout pointed to by `PROTEUS_DIR`, by default a directory named `Proteus` next to this repository, and is skipped when that checkout is not found.

## About this repository

This repository holds the client only. The backend that serves `/api`, the PDF converter and the deployment configuration are private. The client was developed in the same private repository as that server code, so its earlier history cannot be published; this public repository starts at the version that was opened, and development of the client continues here.

At the time of opening the code was left as it was, apart from a few changes made for publication. Two machine-specific paths were removed: `e2e/pdf-unreachable.spec.ts` now finds the converter through `PROTEUS_DIR` and skips without it, and a comment in `playwright.config.ts` lost a home directory path. A photograph of the founders was removed from the about page, which now shows their names and message as text. An unused parser module and the mammoth dependency that only it imported were deleted, together with their entry in the Vite chunk configuration. Two comments, in `public/robots.txt` and `scripts/usecase-jsonld.mjs`, were reworded so that they no longer refer to private documents. A Google Fonts import that no page actually rendered with was removed, and the about page copy was corrected to describe the first-party analytics instead of claiming that no server exists. Three debugging `console.log` calls were removed from the document parser along with an orphaned page-layout module, the text of one test fixture was replaced with invented words of the same shape, and the roadmap page lost its hard-coded vote counts and pre-set vote. The two private environment files were replaced by `.env.example`, the `LICENSE` file and the `license` field in `package.json` (mirrored in `package-lock.json`) were added, `.gitignore` was extended, and this README was written.
